用户 → CDN → 负载均衡(LB) → API网关 → 微服务集群 → 缓存/DB/消息队列

                                              ↓

                                    日志/指标/链路 → 监控告警

Graphene的架构基本就是这个模式的企业级实现，你已经很熟悉了。

## 十一、进阶挑战：复刻Graphene的CDC/CQRS/批处理协调机制

这几项比前面十节的复杂度高一级，属于"理解了Graphene真实架构之后"想加练的内容。

### 11.1 Zorro BLCS —— 自研CDC中间件（原理与Canal一致，已由架构图确认完整链路）

**核心原理**：伪装成MySQL从库，监听主库binlog，把变更事件封装成统一的**ZorroEvent**格式，push到Kafka集群。下游按topic分流，各自独立消费，互不感知：

MySQL主库 \--binlog监听--\> Zorro BLCS工具 \--push ZorroEvent--\> Kafka集群

                                                                  ├── topic: cdc-\*/policy-\*/issuance-\* \--\> CDC微服务 \--write--\> Elasticsearch

                                                                  └── topic: report-blcs-\*            \--\> Alphad微服务 \--mirror SQL--\> CBQ报表库

**两条消费链路的处理方式完全不同**：

- **CDC微服务**：解析ZorroEvent → insert/update/delete ES文档（用于保单列表等查询走ES的CQRS读路径）  
- **Alphad微服务**：解析ZorroEvent → **还原成SQL并直接执行**（execute SQL INSERT/UPDATE/DELETE），把源库的写操作原样"镜像"到CBQ报表库。这种"binlog事件→还原SQL→在目标库重放"的模式，本质是一种自研的**逻辑复制（logical replication）**，效果类似MySQL自身的row-based binlog复制，只是这里是跨系统、经过Kafka中转的版本

**从BLCS-OPS截图确认的关键设计点：**

- **位点(Position) \= MySQL GTID Set**，格式 `{"server-uuid":"事务序号"}`。GTID相比传统"binlog文件名+偏移量"的优势：主从切换后依然全局唯一、单调递增，不会因failover断档。任务重启/恢复时从上次的位点续读。  
- **"自动回补消息"选项**：中断期间漏掉的binlog事件，重启时可选择性回放补发，是CDC链路保证不丢数据的兜底机制  
- **report和cdc是两条独立配置的BLCS任务**，各自单独连只读副本、单独发各自的Kafka topic（如`report-blcs-sli-stg`、`cdc-sli-stg`对应的topic）  
- **过滤维度**：库名表达式 \+ 表名表达式（正则，对应分库分表的数字后缀，如`^air_bcp_0[0-9]*$`）+ 分库分表键（如`holder_customer_id`，供下游做跨分片聚合用）  
- **源库连接用专门的只读账号**（`_ro`后缀），隔离CDC读取对生产主库写路径的影响  
- **"使用zorro格式"选项** \= 是否用ZorroEvent这套统一事件协议封装该filter规则匹配到的binlog变更

**homelab复刻思路**：用开源的 **Canal**（阿里开源，原理与Zorro BLCS一致）模拟生产端——连自己的MySQL、订阅binlog、发Kafka。消费端写两个简单服务：一个模拟CDC微服务（消费后写入本地Elasticsearch）、一个模拟Alphad微服务（消费后把事件还原成SQL在另一个MySQL schema里执行，模拟"报表库镜像"）。这样能完整体验GTID位点、断点续传、以及"同一份变更事件、两种完全不同消费策略"的效果。

**已确认，无需再问同事的问题：**

- [x] report topic谁在消费做重放——**Alphad微服务**，做SQL镜像执行  
- [x] Zorro是什么——统一的CDC事件协议+工具名，不是单纯的"格式选项"

**仍待确认的开放问题：**

- [ ] ZorroEvent具体的schema/字段结构  
- [ ] "分配机器"按钮的机制——是否也是一种服务发现/调度问题，和batch调度的ZK方案能不能类比

### 11.2 ES \+ CQRS —— 读写分离，读强依赖ES

微服务写入MySQL后，主动发Kafka消息，独立的**CDC消费服务**订阅消息、写入ES索引；保单列表等查询直接读ES、不读库。

这是标准的\*\*CQRS（命令查询职责分离）\*\*模式：写路径(Command)→MySQL，读路径(Query)→ES，中间靠异步消息做最终一致(eventual consistency)。

**常见故障点**（如果"经常出问题"，大概率和这几个有关）：

- CDC消费服务延迟/挂掉 → ES数据滞后于真实库，用户刚创建的数据"暂时看不到"  
- Kafka消息丢失/重复消费 → ES索引缺数据或重复  
- 需要确认：有没有定时全量比对库和ES的补偿机制？有没有失败重试/死信队列？

**homelab复刻思路**：一个简单Spring Boot服务，写MySQL后发Kafka消息，另一个服务消费消息写入Elasticsearch，做一个"列表查询走ES、详情查询走MySQL"的小демо，故意让消费者挂掉一段时间，观察"数据不一致窗口"的真实样子。

### 11.3 自研Batch调度 \+ Zookeeper —— 强一致协调 vs K8s原生发现

Batch任务本体分散在各个微服务工程里，独立的调度服务通过**Zookeeper**做服务发现（各微服务注册到ZK的临时节点/ephemeral znode），而不是走K8s Service。

**技术判断**：K8s Service只能回答"路由到一个健康实例"，回答不了"当前有哪些实例、谁是leader"这类需要精确实例清单的问题。批处理调度常见需求——分片调度（任务按ID哈希分片给多个worker）、leader选举（多个调度器实例只能有一个真正下发任务）——天然需要ZK这类**强一致（CP）+ 分布式协调原语**（临时节点、顺序节点、watch机制），而不只是"服务级别的负载均衡"。

**更可能的真实情况**：批处理调度框架的诞生时间早于系统全面上K8s，ZK是框架代码逻辑本身的一部分（可能用了elastic-job/tbschedule之类的开源框架，或者是同样思路的自研版本），不是"团队特意选择两套注册发现"，而是历史遗留+框架绑定的自然结果。

**待确认的开放问题：**

- [ ] batch调度框架是自研还是基于开源框架（elastic-job/tbschedule/xxl-job）二次开发  
- [ ] ZK集群是否有过稳定性问题历史（连接抖动、session超时配置）

**homelab复刻思路**：本地装一个单节点Zookeeper，写一个简单的"多实例注册+leader选举"demo（用Curator框架，是ZK官方推荐的Java客户端库，把临时节点/watch这些概念亲手用一遍），再对比着写一版"纯K8s Service DNS"的等价实现，体会两者的本质区别。

## 十二、更现代的补充方向（现有骨架已经很标准，这几项是真实缺口）

你梳理出来的骨架（网关+微服务+K8s+CDC/CQRS+监控日志）已经是中大型公司的教科书级标准脚手架。以下按优先级排序的几项，是"现代（2026年视角）架构"里真实存在、但目前还没碰过的能力。

### 12.1 分布式事务（强烈建议）

CQRS解决的是"读写分离下的最终一致"，但一个更根本的问题没碰过：**一次业务操作横跨多个微服务的写操作，怎么保证要么都成功、要么都回滚？**（比如"下单"要同时扣库存、扣余额、写订单，任何一步失败前面已经改的怎么撤销？）

单体应用里`@Transactional`一个本地事务就搞定，微服务拆开后没有天然的分布式事务。标准解法：

- **Saga模式**：每一步失败都触发前面步骤的"补偿操作"（比如扣了库存失败要退回）  
- **TCC**：Try-Confirm-Cancel三阶段

**homelab思路**：用 **Seata**（阿里开源，最主流实现）接入你阶段2写的"下单+扣库存"玩具微服务，故意让某一步失败，观察补偿机制怎么把前面的操作撤销。

### 12.2 灰度发布/蓝绿部署（强烈建议）

目前CI/CD是"构建→直接部署"，生产标准做法是**先给一小部分流量验证新版本，没问题再全量切换**——灰度发布(canary)、蓝绿部署(blue-green)。

**homelab思路**：K8s原生可以用Service权重路由简单模拟；进阶用 **Argo Rollouts**，体验"能上线"和"敢上线"之间的差距。

### 12.3 压测与混沌工程（强烈建议，对SRE方向尤其重要）

现在的监控是"事后观察"，更进阶的SRE能力是**主动验证系统在压力/故障下的表现**：

- **压测**：k6、JMeter、Gatling——测极限QPS、找性能瓶颈  
- **混沌工程**：ChaosBlade（阿里开源）、Chaos Mesh——主动注入故障（杀Pod、模拟网络延迟、模拟DB连接池耗尽），观察系统能不能自愈、告警能不能及时发现

**homelab思路**：先用k6对阶段2的玩具服务做一次简单压测，再用Chaos Mesh在K8s里随机kill掉一个Pod，观察Prometheus/Grafana告警链路是否真的触发——这是把"RCA能力"从被动等故障，变成主动练手感的最直接方式。

### 12.4 Service Mesh（进阶可选）

Spring Cloud Gateway+Feign这套，熔断/重试/超时/加密这些能力要在业务代码里手动接入。**Service Mesh（Istio）** 把这些能力下沉到基础设施层（每个Pod旁挂一个sidecar代理，业务代码无感知），是云原生圈子更前沿的服务治理方式。不是说Spring Cloud过时（Graphene本身就这么用），是"体验另一种更现代的做法"。

### 12.5 OLAP报表引擎（进阶可选，呼应你的CBQ报表库话题）

Alphad镜像到MySQL能跑，但MySQL本质是为事务优化的行式存储，海量聚合查询（"这个月所有分公司保费汇总"）会比列式存储的OLAP引擎慢很多。现代做法更倾向用**ClickHouse、Apache Doris**这类专门的分析引擎承接报表查询。这一项和下面的"大数据平台"直接相关，建议放在一起练。

## 十三、大数据平台（新增模块）

前面的架构解决的是"单笔业务怎么正确处理"，大数据平台解决的是\*\*"海量历史数据怎么批量/实时分析出business insight"\*\*——这是很多公司里和"业务系统"完全独立的另一套技术栈，但数据来源可以完全复用你已经搭好的CDC/Kafka链路，性价比很高。

### 13.1 大数据平台的标准分层

> **历史背景小知识：Hadoop**——大数据平台的"祖师爷"，2006-2013年代的标准三件套：**HDFS**(分布式文件系统，管"数据存哪")+**MapReduce**(计算框架，管"数据怎么算，但每步都要落盘，较慢")+**YARN**(资源调度，管"任务分给集群哪台机器")。现代大数据栈是这三个组件被逐个替换的产物：HDFS→MinIO/S3(更轻量、云原生)，MapReduce→Spark(基于内存计算，快一个数量级)，YARN→K8s(容器编排统一收编)。骨架逻辑是Hadoop发明的，但具体实现已经换代。下表直接给现代方案，homelab不建议花时间部署Hadoop本身，但如果以后工作中遇到还在用Hadoop/Hive的老系统（不少传统大厂数据平台历史包袱较重，至今还在用），至少要认得这套术语。

| 层 | 作用 | 技术选型 |
| :---- | :---- | :---- |
| **数据采集层** | 从业务系统抓数据 | 复用你已有的 **Canal(模拟Zorro BLCS) \+ Kafka**，同一份binlog事件，多一个消费者接进大数据平台 |
| **存储层——数据湖** | 存海量原始数据，格式灵活、成本低 | **MinIO**（开源、兼容S3协议，本地实验室的最佳选择） |
| **存储层——数据仓库/OLAP** | 存结构化后的数据，供高速分析查询 | **ClickHouse** 或 **Apache Doris**（列式存储，专为聚合查询优化） |
| **批处理计算引擎** | 离线，处理"昨天一整天的所有数据" | **Spark**（业界标准，尤其Spark SQL） |
| **实时流计算引擎** | 实时，处理"现在正在发生的数据流" | **Flink**（可以直接消费你Kafka里的CDC事件，做实时聚合，如"实时保费统计"） |
| **任务调度** | 定时触发ETL任务（不同于你的业务batch调度，这里调度的是数据处理任务） | **Airflow**（业界标准，DAG可视化） |
| **元数据管理/数据目录** | "这个表是什么意思、字段含义是什么、谁在用" | DataHub（进阶可选，先不装也行） |
| **BI/可视化** | 给业务方看报表、做图表 | **Superset**（开源，Apache基金会项目，上手快） |

### 13.2 和你现有架构的连接点（这是最有价值的部分）

你不需要凭空造数据——**直接复用阶段4搭的Kafka \+ Canal CDC链路**，同一份binlog变更事件，除了原有的"写ES"消费者，再加一个"写进数据湖/触发Flink实时计算"的消费者。这样能真实体验"同一份数据，业务系统看它是CQRS的一环，大数据平台看它是分析数据源"这个视角切换。

### 13.3 建议的搭建顺序

1. **MinIO**（数据湖，最简单，先把"数据能落地"这件事跑通）  
2. **ClickHouse**（OLAP引擎，直接把之前Alphad镜像的报表数据换个目的地，从MySQL换成ClickHouse，对比查询速度差异——这是最直观的"为什么需要OLAP"的体验）  
3. **Flink**（实时流处理，消费Kafka里的CDC事件，做一个"实时保费金额滚动汇总"的小demo，写入ClickHouse）  
4. **Superset**（连上ClickHouse，5分钟拖拽出一个仪表盘，成就感最强的一步）  
5. **Airflow**（进阶，编排"每天凌晨跑一次的全量对账/汇总任务"，可以对比你之前了解的Graphene自研batch调度，体会"数据ETL调度"和"业务批处理调度"的设计差异）  
6. **Spark**（最后加，批处理引擎跟Flink有一定概念重叠，放在流处理练熟之后理解会更快）

## 十四、AI 与向量数据库（新增模块，从零开始讲清楚）

这块你完全没接触过，我从概念讲起，尽量讲透。

### 14.1 先搞懂核心概念

**向量(vector)/embedding 是什么**：把一段文字（或图片）丢给一个"embedding模型"，模型会输出一串数字（比如1536个浮点数），这串数字代表这段文字的"语义"。关键性质是：**语义相近的文字，转出来的数字串在数学上也相近**（可以用余弦相似度衡量"有多近"）。比如"保险理赔"和"索赔申请"这两个词字面完全不同，但转成向量后，数学距离会很近。

**向量数据库是什么**：传统数据库（MySQL）擅长"精确匹配"（`WHERE id=123`）；向量数据库擅长"相似度检索"（"给我找语义上最像这句话的100条记录"）。这是完全不同的索引结构和查询方式。

**RAG（检索增强生成）是什么**：这是目前AI应用最核心的模式，解决"LLM不知道你私有数据、知识会过时"的问题，流程是：

1. 把你的私有文档（比如你的SLI-BAT001这些规范文档）切成小段，每段转成向量，存进向量数据库  
2. 用户提问时，先把问题也转成向量，去向量数据库里找"最相似的几段原文"  
3. 把这几段原文 \+ 用户问题，一起丢给LLM，让LLM"参考这些资料回答"

这样LLM回答时用的是你真实的私有资料，而不是凭训练记忆瞎编（幻觉），这也是解决"LLM知识过时"问题最主流的办法。

### 14.2 你的架构里需要新增的模块

| 模块 | 作用 | 技术选型 |
| :---- | :---- | :---- |
| Embedding模型 | 把文字转成向量 | 可以直接用你以后要装的**Ollama**跑本地embedding模型（如`nomic-embed-text`），不用调用付费API |
| 向量数据库 | 存向量、做相似度检索 | **pgvector**（PostgreSQL的插件，最适合homelab起步——你已经会用关系型数据库，装个插件就能有向量能力，不用学一整套新系统）；进阶可选**Milvus**（专业向量数据库，功能更全但部署更复杂） |
| LLM推理服务 | 生成最终回答 | **Ollama**（你长期规划里已经提到的，本地跑开源模型） |
| **编排框架** | 决定"什么时候调LLM、调之前查不查资料、要不要调用工具、结果怎么处理"——胶水逻辑标准化 | **LangChain**（适合链式/线性流程，RAG这种"查资料→喂LLM→出结果"很适合）、**LangGraph**（适合有循环/条件判断的图状流程，是目前做Agent智能体的主流框架） |
| AI网关（进阶可选） | 统一管理多个LLM调用的限流/路由/成本追踪 | **LiteLLM Proxy**（开源，把不同厂商的LLM API统一成一套接口） |

### 14.2.1 编排框架到底解决什么问题

不用编排框架，也能手写代码实现RAG（查向量库→拼prompt→调LLM），但流程一旦变复杂（"先判断问题属于哪类知识库，再决定查不查资料，查完可能还要调用计算器/查天气之类的外部工具，最后再总结"），手写的if-else会迅速失控。

- **LangChain**：把常见步骤（加载文档、切分、embedding、检索、拼prompt、调LLM、解析输出）封装成可组合的"链(chain)"，线性/简单分支流程写起来很快  
- **LangGraph**：把整个流程建模成一个**状态机**，支持循环、条件跳转、"来回试几次直到满意"——**Agent（智能体，也就是"LLM自己决定下一步调用哪个工具、要不要重试"这种更自主的流程）现在业界基本都在用LangGraph或类似框架**（比如OpenAI的实现、CrewAI这类竞品）

两者不是二选一，很多实际项目是LangChain处理简单RAG部分，LangGraph处理更复杂的多步骤Agent逻辑。

### 14.3 建议的搭建顺序（从最简单能出效果的开始）

1. **PostgreSQL \+ pgvector插件**（比装专业向量数据库简单得多，先用最小成本把"向量检索"这件事跑通）  
2. **Ollama跑一个小的embedding模型**，写一个小脚本，把你的BSD学习文档（比如SLI-BAT001）按段落切开，转成向量存进pgvector  
3. **写一个简单的检索demo**：输入一句话（比如"保全变更的处理流程是什么"），从pgvector里检索出最相关的几段原文，先只做到"检索"这一步，验证"语义相似"这件事真的work  
4. **接上Ollama的对话模型**，把检索出来的原文 \+ 你的问题一起丢给它，完整跑通一次RAG流程——**这一步做完，你就有了一个"能回答BSD规范问题的私有AI助手"，直接对你现在的BSD学习有实用价值**  
5. （进阶）如果以后PC配了3090，同样这套RAG流程可以直接换成跑更大的本地模型，效果会好很多

### 14.4 这块能反哺你已有的两个项目

- **BSD学习**：把你已深度学习的SLI-API/BAT/ACC/USR文档全部灌进去，做一个你专属的"保险业务知识问答助手"  
- **牛马チャン家族**：如果以后想给网站加"语义搜索故事内容"或者简单的角色问答互动，这套RAG的经验直接能复用
